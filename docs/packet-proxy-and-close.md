# WeakProxy open and receipt-gated close

Baseline is 3.70 / 924dd034e99b479eb3b31a2f94f1807d685dcdb9; 3.80 is the WeakProxy-open candidate. The user's current device report is that opening now works but closure does not, the experience feels slow, and self-sent packets are skipped. No 3.80 close-phase trace was supplied, so those symptoms do not prove whether the model receipt changed or which UI binding survived. The current candidate rescans for a newly-created close control after the open action and shortens bounded scan intervals. Self-sent handling gets a separate account-scoped opt-in in the same panel; default remains off.

## Primary evidence in the locked TIM 4.1.0.81 Mach-O

WeakProxy -target: @16@0:8, IMP 0x10013e018. -forwardingTargetForSelector:: @24@0:8:16, IMP 0x1003a6a5c. These two routines load the same weak ivar through the same helper and return it; the forwarding path ignores the selector. The class's -methodSignatureForSelector: at 0x1003a6ae8 produces a generic constant signature, not the true action ABI. Never use it to authorize dispatch. User trace supplies the exact openButtonClick/dismissView bindings; they are not speculative selectors.

The implementation permits one unwrap only for the exact runtime WeakProxy class after checking both accessor/forwarder encodings. It retains the getter result while comparing the forwarding result, rejects nil/self/nested/changed targets, and validates the real declared action's void return, arity and object argument encodings. It still sends the original UIControl TouchUpInside event through the proxy rather than bypassing it. An image-only open is allowed only for the exact observed WeakProxy -> openButtonClick binding plus the existing new-view, unique-binding, visibility, foreground/account/setting and Wallet module checks. Arbitrary forwarding proxies, inferred signatures and fuzzy selector matches are rejected.

## Close confirmation and limitations

The close action must be the exact registered dismissView binding on one unique, visible, newly observed control in the active window. The scan is repeated only after local receipt confirmation, so it tolerates the result page appearing in a replacement controller or a close control being recreated during the native transition. The target and implementation must validate against the Wallet module; multiple dismiss bindings or a target outside that module are rejected. A new route cannot overlap an opened pending packet. User interaction cancels automatic steps.

A nil-error callback or an open method returning is not receipt evidence. Auto-close additionally requires the same native OCWalletElement received by this route to transition from grabbedAmount == 0 to grabbedAmount > 0, through its verified Q16@0:8 getter (0x10a28002c). Production never writes the field or invents grabState enums. A native error veto is latched. The observation is a native local received-amount model signal, not independent server settlement proof. Open-button discovery now polls from 0.08s through 1.8s; after confirmed receipt, the close-control scan starts at 0.12s and is bounded through 8s. These are best-effort UI observation windows, not a claim about network/server latency. If model state stays unchanged, an error occurs, the receiver/module is ambiguous, or no safe close control is found, the page remains available to the user.

The account-scoped self-sent setting is independent from the normal auto-claim switch and defaults off. A packet is considered self-sent only when its validated record sender UID exactly equals the current account UID; missing/ambiguous identity still skips it. Both switches must be on before the native route, follow-up open, or close checks can proceed. This only enables TIM's ordinary receive route for eligible, newly delivered self-authored packets; it does not bypass TIM eligibility, limits, or claim UI. No support for historical/resend packets is inferred.

The dynamic Wallet UI implementation was not supplied. Whether real TIM updates the same wallet object, replaces controls inside the new page root, and actually credits receipt remains device-untested. It may replace the opened target object or present a separate controller; auto-close deliberately does not guess navigation/pop/dismiss APIs. Optional diagnostics retain only fixed state labels and runtime identifiers, never amount values, account IDs, message contents or credentials.

## Regression

The real UIKit fixture now uses actual weak target forwarding, an image-only UIButton with openButtonClick, and a distinct dismissView close button which is removed/recreated during claim. It requires private/group and self-authored private/group routes to open and close once, validates the self-sent opt-in is separate and off by default, and rejects a nil weak receiver, an incompatible BOOL action behind a dummy void signature, a nil-error callback with no model receipt, and a native error despite a positive model field. Manual-cancel, ambiguity, payment, and foreground-token protections remain. Fixtures are not real TIM device acceptance.
